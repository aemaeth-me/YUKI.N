## 一、原则

1. **orchestration 优先**：首屏回答「各位 Yuki 正在干什么」。对话、配置、
   记忆都是钻取目标，不是首页。
2. **状态丰富、来源诚实**：每个活跃 Run 展示阶段、轮次、token、上下文、
   进行中工具、耗时、Worker 数——全部来自遥测投影（Specs §1.4），没有
   数据的位置显示空缺，不用模型自述或猜测补空。来源完整性存疑时明示
   （如「shell 造成的变更未经追踪」）。
3. **对话是组件**：主对话与任务对话共用 `<ConversationPanel>`，嵌入工作
   台与任务详情；它不再提供页面骨架。
4. **钻取一致**：集群卡片 → Yuki 工作台 → Run 监控，三层下钻；任何状态
   卡、交付项、变更项都能进入其来源（Run 监控 / 任务详情 / artifact）。
5. **等待事项显式化**：派发草案、request_confirmation、失败告警在集群
   总览、工作台、Run 监控三级都有入口与计数。
6. **单流驱动**：实时状态统一来自 `/activity/stream`；降级轮询是异常态
   而非常态，且必须可见地标明。

## 二、信息架构

```text
/fleet                          集群总览（默认落点）
└── /yuki/:id                   Yuki 工作台
    ├── ?view=now               现在（默认）
    ├── ?view=chat              主对话
    ├── ?view=tasks             任务列表
    ├── ?view=tasks/:tid        任务详情（对话 / 交付 / 变更 / 配置 四页签）
    ├── ?view=deliveries        交付
    ├── ?view=changes           变更
    ├── ?view=memory|self|audit 既有能力（二级导航）
    └── ?view=run/:runId        Run 监控（从任何状态卡进入；也可单独直达）
```

- 路由：从当前的 Page 枚举改为**真实 URL 路由**（`Browser.application` +
  pushUrl）。刷新/深链必须还原同一视图——工作台是可监控对象，URL 是其
  引用方式。
- localStorage 只保留非 URL 偏好（面板折叠、上次排序）；`yuki.n/threadId`
  默认落点语义废除。
- 视图切换不丢订阅：`/activity/stream` 在应用生命周期内全局单连接。

## 三、视图规格

### 3.1 集群总览 /fleet

数据源：FleetSnapshot（首帧）+ 监控流增量。

```
┌─────────────────────────────────────────────────────────┐
│ YUKI.N                    ● 实时连接正常（或降级标记）    │
├─────────────────────────────────────────────────────────┤
│ ┌ Yuki 卡片 ────────┐ ┌ Yuki 卡片 ────────┐             │
│ │ 名字  ●活跃/◌等待/○空闲                      │             │
│ │ 正在：2 个任务 · 3 个 Worker                │             │
│ │ ▸ 状态最前的 Run 摘要（objective + 阶段）    │             │
│ │ ▸ token 用量合计 / 已耗时                    │             │
│ │ ⚠ 1 份派发草案待确认                         │             │
│ │ 最近交付：答案「…」· 文件 main.hs · 2 分钟前 │             │
│ └───────────────────┘ └───────────────────┘             │
│ 事件带（全局）：交付 / 草案 / run.end / 失败告警，时间序   │
└─────────────────────────────────────────────────────────┘
```

- 卡片排序：active > waiting > idle，同级按最近事件时间。
- 点击卡片 → 该 Yuki 工作台（now）。
- 点击卡内 Run 摘要 → 直达 Run 监控；点击草案提醒 → 工作台并弹出派发
  对话框。
- 空态：无 Yuki → 创建入口（沿用既有创建语义）；无活跃 → 卡片显示
  「空闲」与最近交付时间。
- 「+ 新 Yuki」入口常驻顶栏。

### 3.2 Yuki 工作台 · 现在（now）

数据源：ActivitySnapshot + 监控流（按 incarnation 过滤）。

```
┌ 顶栏：Yuki 名 · now/chat/tasks/deliveries/changes ··· 导航 ┐
├ 等待用户（如有）──────────────────────────────┤
│ ⚠ 派发草案「标题」  [查看]   ⓘ request_confirmation ×1     │
├ 活跃 Run 树──────────────────────────────────┤
│ ● 主对话 Run        状态卡（§3.6）                          │
│ ● 任务「标题」Run   状态卡（§3.6）        [进入任务]        │
│   └─ ● Worker      状态卡（§3.6，缩进嵌套）                │
│      └─ ● Worker（depth>1 时继续嵌套）                     │
├ 最近交付（5 条）──────────────────────────────┤
└───────────────────────────────────────────────┘
```

- Run 树按 parentRunId 组；Worker 依附所属 Run 卡片缩进。
- 空闲态：显示「当前没有进行中的工作」+ 主对话入口 + 最近交付。
- 该视图不轮询；完全由监控流驱动（快照仅初始）。

### 3.3 Yuki 工作台 · 主对话（chat）

- `<ConversationPanel>` 承载 Home（`threadId=home-<id>`）：流式消息、
  推理、工具卡、SubAgent 卡、确认卡、steering、取消、重试——交互能力
  与既有对话一致。
- 顶栏常驻「派发任务」按钮 → 派发对话框（§3.7）。
- [P2] `dispatch.draft` 事件在流内渲染**派发卡片**：title/prompt/能力快照
  可编辑 + 确认/取消；终态后锁定（`draft.resolved` 或 confirm 响应）。
- Home 态不显示归档/fork 按钮。
- 主对话 Run 活跃时，其状态卡固定在对话顶部（与 now 视图同一组件）。

### 3.4 Yuki 工作台 · 任务列表（tasks）

- 数据源：`GET /threads?kind=task` + 监控流补充活跃标记。
- 行项：标题、状态徽标（运行中 / 等待确认 / 空闲 / 已归档）、最后活跃
  时间、最近交付摘要、run 计数（journal）。
- 排序默认按最后活跃；支持过滤归档。
- 既有操作保留：新建（直接进入，不经派发——见 §九 权衡）、重命名、
  归档/恢复、fork、导入/导出，收进行内菜单。

### 3.5 任务详情（tasks/:tid）

```
┌ 任务头：标题 · 状态徽标 · 配置入口 · 菜单（归档/fork/导出） ┐
│ 活跃时：根 Run 状态卡（§3.6）                                │
├ 页签：对话 | 交付 | 变更 | 配置 ───────────────────────────┤
```

- **对话**：`<ConversationPanel>`（同主对话）；确认派发后的自动首 Run 在
  此发起（条件：transcript 末条为未应答 user message）。
- **交付**：该任务过滤的 DeliveryRecord 流（§3.8 组件）。
- **变更**：该任务过滤的 FsChangeRecord 流（§3.9 组件）。
- **配置**：既有能力页内容（cwd、provider/model/effort、gate、上下文
  策略），原样迁入页签。

### 3.6 RunStatusCard（核心复用组件）

每个活跃 Run 一张，全部数据来自 LiveStatus：

```
┌ ● objective（截断两行）                        阶段徽标 ┐
│ 轮次 7/32 · 模型 deepseek-v4-flash · 12.4k tok ↑ 3.1k ↓ │
│ 上下文 ▓▓▓▓▓░░░ 62%（估算 610k / 触发线 984k）           │
│ ⚙ fs_write（12s）  ⚙ shell（3s）     ← 进行中工具        │
│ 已耗时 4m 12s · Worker ×3 · 最近活动：tool:fs_write     │
│ [监控] [steer] [取消]                                    │
└──────────────────────────────────────────────────────────┘
```

- 阶段徽标：running / awaiting-tool / compacting / sleeping / cancelling，
  颜色与动效区分（sleeping 用静态标记，不用闪烁）。
- 已耗时、工具耗时由前端按 startedAt/lastEventAt 本地插值秒级刷新。
- 上下文条仅在 liveContext 存在时显示；usage 为零时不显示 token 行。
- 「监控」→ Run 监控；「steer」展开行内输入（`POST /agent/steer`，
  runId=该 Run，Worker 同样直达）；「取消」二次确认。
- Worker 卡片与根 Run 同组件，缩进 + Worker 徽标。

### 3.7 派发对话框

主对话「派发任务」→ 输入需求 → `POST dispatches` → 对话框：

- title（单行）、prompt（多行编辑器）；
- 能力快照区：provider / model / effort、cwd、fs / shell / memory gate、
  上下文策略（复用现有能力页控件，抽出 `<CapabilityFields>`）；
- 生成说明行：「由模型起草 / 模型不可用，已按原文生成」（generation）；
- [确认派发] → confirm → 跳任务详情（对话页签）；
- [存为草案] 仅关闭（PATCH 已自动保存）；[取消] → cancel API。
- 同一 Yuki 存在多份 draft 时，工作台「等待用户」区可重开任一份。

### 3.8 交付视图（deliveries / 任务页签复用）

- 时间倒序流：类型图标（答案 / 文件 / artifact）、标题、所属任务、run
  链接、时间、大小。
- 展开：答案 → 对应 transcript 定位；文件 → diff 或路径复制；
  artifact → `GET /artifacts/:id` 内容查看。
- 过滤：按任务、按类型；分页游标 `before`。

### 3.9 变更视图（changes / 任务页签复用）

- 时间倒序流：路径、操作徽标（created / modified / deleted）、来源徽标
  （工具名 / git）、所属任务、时间。
- 展开：unified diff 渲染（语法高亮，逐行 +/-）；git 来源只显示 stat 行
  并注明「由 git 补记，内容以工作区为准」。
- 任务含 shell 调用且 cwd 非 git 仓库 → 视图顶部固定提示
  「该任务中 shell 命令造成的文件变更未经追踪」。

### 3.10 Run 监控（run/:runId）

钻取终点，面向单个 Run（根或 Worker）：

```
┌ 状态头：RunStatusCard 数据 + outcome（终局后）─────────────┐
├ 事件时间线（活跃：POST /agent 流；历史：journal trace）──────┤
│ 消息 / 推理 / 工具调用（参数+结果+artifact 链接）/ Worker 节点 │
├ Worker 子树：本 Run 派生的 Worker 状态卡                     │
├ 交付与变更：本 Run 过滤                                      │
├ steering 输入 · 取消 ·（历史 run 显示 run trace 与重放入口）──┤
```

- 活跃 Run 的事件正文来自其 SSE 流（若当前连接未持有该流——例如监控
  其他 Yuki 的 Run——则显示「该 Run 正在另一连接中执行」+ 状态卡数据 +
  可 steer/取消；不强行多路订阅事件正文）。
- 历史 Run 用既有 `GET /journal/runs/:id/trace` 渲染同一时间线组件。

### 3.11 二级导航（记忆 / 自我 / 检查）

既有 Memory / Self / Audit 视图内容不变，迁入工作台二级导航；布局随新
骨架适配。其信息架构与组件可以后续再演进，本轮只做迁移，不重设计。

## 四、组件清单（Elm 模块划分）

```text
Yuki.App.*               应用骨架：路由、顶栏、实时连接状态、降级标记
Yuki.Fleet.*             集群总览
Yuki.Workbench.*         工作台框架：导航、等待用户区、now 视图
Yuki.Run.StatusCard      RunStatusCard（§3.6）
Yuki.Run.Monitor         Run 监控（§3.10）
Yuki.Run.Tree            Run 树组装（parentRunId 分组）
Yuki.Conversation.*      对话面板（消息流、工具卡、SubAgent 卡、输入区）
Yuki.Dispatch.*          派发对话框、派发卡片、草稿列表
Yuki.Delivery.*          交付流与详情
Yuki.Changes.*           变更流与 diff 渲染
Yuki.CapabilityFields    能力快照表单（能力页/派发对话框共用）
Yuki.Memory|Self|Audit   既有视图迁移
Yuki.Telemetry.*         监控流解码、FleetSnapshot/ActivitySnapshot 状态归并

```

- 废弃现有单一巨型 `Model`：各视图拥有自己的 State，全局只保留
  `TelemetryState`（runId → LiveStatus、fleet 摘要、连接态）与路由。
- 对话面板是带独立 Model/Msg 的组件，由工作台/任务详情各持有一份实例。

## 五、状态与数据流

```text
/activity/stream ──► TelemetryState（全局单例）
                      ├── runs: Dict runId LiveStatus
                      ├── fleet: Dict incarnationId FleetEntry
                      ├── deliveries / fsChanges（视图窗口缓存，分页另查）
                      └── conn: Live | Degraded | Offline

POST /agent（某 ConversationPanel 发起）──► 该面板私有的事件流状态
inspect 通道（既有）──► 一切非 SSE 请求
```

- **Telemetry 归并**：snapshot 帧全量替换；status 帧按 runId upsert；
  run.end → 移除并标记终态（短暂保留灰色卡片 30s 便于感知）；delivery /
  fschange → 追加到对应视图窗口（窗口外丢弃，视图进入时经 §2.6 端点拉
  取）。
- **节流配合**：后端 status 帧已 200ms 合并；前端对同一 runId 的连续帧
  直接替换，不做动画队列。
- **本地插值**：耗时类显示由 1s ticker 按 startedAt/lastEventAt 计算，
  不依赖推送频率。
- **降级**：EventSource onerror 连续 3 次 → Degraded：3s 轮询
  `GET /fleet`（总览）或 `GET /incarnations/:id/activity`（工作台），顶栏
  显示「实时连接已降级，3 秒轮询中」；恢复后自动切回。
- **乐观更新**：steer / cancel / confirm 立即反映本地状态，失败回滚并
  提示。
- **多标签页**：第二标签页打开时各自建立监控流连接（hub 广播天然
  支持）；`POST /agent` 对同一 thread 的并发发起不做限制（现状语义）。

## 九、已确认的权衡

- **任务仍可手动创建**（任务列表页内菜单）：派发是主路径，手动创建是
  高级路径（无草案、无确认，直接建空任务）。理由：既有导入/迁移与调试
  场景需要；UI 上不给予与派发同等的显著性。
- **监控流不承载事件正文**：Run 监控的事件时间线在「当前连接持有该
  Run」时才实时；其余场景显示状态卡 + 可操作。避免前端为每个活跃 Run
  维持一条 SSE。
- **Worker 详情**：同步 Worker 的过程在父流内（既有 SubAgent 卡）；
  [P2] 异步 Worker 的过程经 Run 监控（journal trace）查看，不在父对话
  流内渲染。
