## 一、目标

把 YUKI.N 从「选择 Yuki → 创建/进入任务 → 对话」演进为**以 orchestration 为
重心的 Agent 集群产品**：

1. **多 Yuki、多任务、Agent 集群**：产品主体是若干持续存在的 Yuki 及其正在
   运行的工作集群，而不是一系列对话。
2. **可观测性是头等大事**：用户随时看到各个 Yuki 正在干什么——不是「运行中」
   一句话，而是对用户有价值的丰富状态：当前阶段、轮次、token 与上下文用量、
   进行中的工具、耗时、Worker 树、等待用户裁决的事项。
3. **交付可见**：每个 Yuki 交付了什么——最终回答、生成的文件、artifacts——
   形成可检索的交付流。
4. **文件系统变化可见**：按任务/Run 维度追踪文件的创建、修改与删除，
   可展开 diff。
5. **主对话**：每个 Yuki 仍有默认的主对话（主 Agent），用户在此聊天、派发
   任务、接收 Yuki 的派发提议；但对话是工作台内的一种交互组件，不再是
   信息架构的中心。
6. **三层编排**：主 Agent → 任务 Agent（Orchestrator）→ Worker Subagent；
   父子之间可通信，具备常规 orchestration 能力。

非目标（本轮不做）：

- 记忆质量、召回策略、睡眠机制的优化（见 memory/05-演进方向）。
- 蓝图完整的 Delegation Spec / Work Graph / Acceptance / 预算体系（P3 对齐）。
- 多用户、鉴权、跨机调度；YUKI.N 仍是本地单用户工具。
- Worker 持久化为新 Yuki 的晋升流程。

## 二、现状与差距

现有机制（实现细节见源码）：

- 层级：`Incarnation > Thread(任务) > Run > sub_agent`。
- `sub_agent`（`src/Yuki/N/SubAgent.hs`）是 Run 内**同步阻塞**工具：子 Run
  共享父 threadId，继承裁剪后的工具集（`workerDeniedTools` 禁写记忆/身份/
  睡眠），事件以 `agent.sub` CUSTOM 事件包装进父 SSE 流，深度受
  `YUKI_SUBAGENT_DEPTH`（默认 1）限制。子 Run 注册进共享 `RunRegistry`。
- `RunRegistry`（`src/Yuki/N/Runs.hs`）持有每个活跃 Run 的线程、steering 与
  follow-up 队列；Journal 的 scope 已天然记录 Run 树。
- `AgentHooks.observeEvent` 已是统一的事件观察点；`beforeToolCall` /
  `afterToolCall` hook 已存在。
- 前端：对话为主体的单页应用（Conversation 是中心页，Tasks/Memory/
  Capabilities/Self/Audit 围绕它），已有 SubAgent 卡片与
  `request_confirmation` 确认机制。

差距：

1. **UI 架构错位**：现有 UI 以对话为主体组织，与「多 Yuki、多任务、Agent
   集群、orchestration 为重心」的产品方向不协调。本轮前端**整体重写信息
   架构**，不复用现有页面骨架（可复用的仅限底层机制：SSE 解析、AG-UI 事件
   解码、消息渲染件、主题，见 `04-前端架构.md` §八）。
2. 没有主对话实体：选择 Yuki 后只能进入某个任务。
3. 没有任务派发流程：无草案、无确认、无能力继承快照。
4. `sub_agent` 只能同步阻塞：父 Run 无法异步派出 Worker、无法与其通信、
   无法查询状态；`Experience` 预留的 `delegationId` 从未被填充。
5. 没有 Run 树索引与实时状态投影：前端无法回答「这个 Yuki 正在跑什么、
   跑到哪一步、花了多少 token、哪个工具正在执行」。
6. 没有交付与 FS 变更记录：任务做完留下了什么文件、改动了什么，系统
   不追踪、不可见。

## 三、核心概念与层级模型

```text
Yuki（Incarnation）                     持久主体：人格、记忆、能力默认值
├── 主对话（Home）                      主 Agent 的会话；唯一、持久、非任务
│   └── Run（主 Agent Run）             聊天、判断、提议派发、可直接用 sub_agent
├── 任务（Task，kind=task 的 Thread）   派发产生；持久工作单元
│   └── Run（任务 Agent Run）           任务 Orchestrator；用 sub_agent 拆解工作
└── Worker（Subagent Run）              某次 Run 的临时执行者；不形成持久主体
```

命名边界：

- **主 Agent**：在 Home 会话中代表该 Yuki 的根 actor。产品上就叫「这个 Yuki」。
- **任务 Agent**：某个派发任务内的根 actor，是该任务的 Orchestrator。继承
  Yuki 的人格（同一 incarnationId、同一认知体系）与派发时确认的能力快照。
- **Worker**：由 `sub_agent` 族工具派生的临时 Run。默认不可再委派
  （`YUKI_SUBAGENT_DEPTH=1`）。

关键辨析：

- **主对话不是任务**，但实现上复用 Thread（`kind=home`）。这保证记忆闭环
  （run close → Task Archive → Experience → Impression）、SSE、steering、
  取消、睡眠、上下文压缩全部零改动。蓝图中「Intent ≠ Task / Direct Run」
  的纯粹形态留作远期；Home Thread 在语义上向其收敛：不出现在任务列表、
  不可归档、不可删除、不可 fork。
- **派发任务 vs sub_agent**：派发任务创建**持久任务**（新 Thread，可暂停、
  恢复、归档，有自己的界面与 Transcript）；sub_agent 创建**临时 Worker**
  （Run 内执行者，随父 Run 消亡）。主 Agent 两者皆可：闲聊中的重活派任务，
  轻量杂务用 Worker。
- **任务 Agent 的 Run 与主 Agent 的 Run 是平级根 Run**，各自独立的 SSE
  连接、steering 队列与取消。

## 四、产品形态：集群总览与 Yuki 工作台

前端信息架构整体重写（完整视图与组件规格见
[`04-前端架构.md`](04-前端架构.md)）：

```text
集群总览（默认落点）
│   全部 Yuki 的实时状态卡片：在跑什么、跑到哪一步、等待什么、最近交付
│
└── Yuki 工作台
    ├── 现在      活跃 Run 树 + 每个 Run 的实时状态卡 + 等待用户裁决事项
    ├── 主对话    与该 Yuki 的默认交互；派发入口；提议卡片
    ├── 任务      全部任务：状态、最后活跃、最近交付
    ├── 交付      答案 / 文件 / artifact 交付流，按任务过滤
    ├── 变更      FS 变更流：路径、操作、diff，按任务/Run 过滤
    ├── 记忆 / 自我 / 检查   既有能力，降入二级导航
    └── Run 监控  任一 Run 的钻取视图：状态头 + 事件时间线 + Worker 子树
                  + steering + 该 Run 的交付与变更
```

原则：

1. **orchestration 优先**：首屏回答「各位 Yuki 正在干什么」，而不是打开某个
   对话框。
2. **状态必须丰富**：每个活跃 Run 展示阶段（running / awaiting-tool /
   compacting / sleeping）、轮次 x/y、模型、累计 token、上下文用量、进行中
   的工具调用、已耗时、活跃 Worker 数。
3. **对话是组件**：主对话与任务对话使用同一对话组件，嵌入工作台与任务
   详情，不再是页面骨架。
4. **钻取一致**：集群卡片 → Yuki 工作台 → Run 监控，三层下钻；任何状态卡
   都可进入对应 Run 监控。
5. **等待事项显式化**：派发草案、`request_confirmation`、失败告警在各层级
   都有明确入口，不能埋在事件流里。

## 五、主对话（Home）

- 每个 Incarnation 有且仅有一个 Home 会话，首次访问时幂等创建
  （`GET /incarnations/:id/home`）。
- `SessionMeta` 增加 `sessionKind = Home | Task`（持久化缺省 `Task`，完全
  向后兼容；存量 Thread 自动视为 Task）。
- Home 会话：不出现在任务列表；归档/恢复/删除/fork/导入覆盖均拒绝（400）；
  删除 Yuki 时随之一并删除。
- Home 会话的 ThreadConfig 视为**该 Yuki 的默认能力配置**：派发任务时的
  继承来源（见 §6.3）。
- 认知行为与普通会话一致：同一 incarnationId 的 compile、记忆工具、睡眠、
  印象激活全部生效。
- 产品上，主对话是工作台「主对话」视图，也是用户与该 Yuki 的默认交互
  界面；聊天不产生任务。

## 六、派发任务（Dispatch）

### 6.1 两步事务

```text
用户（或 Yuki）发起
→ 生成 DispatchDraft（标题、任务 Prompt、能力快照）
→ 用户在派发对话框中修改 / 确认
→ confirm：创建任务 Thread + 写入首条任务指令
→ 进入任务视图，任务 Agent 开始首个 Run
```

- 派发**不**静默发生。除 confirm 外没有任何路径能创建派发任务；Yuki 的
  提议同样必须经用户确认（见 §6.4）。
- DispatchDraft 持久化（`dispatches.json`）：刷新、重启不丢；生命周期
  `draft → dispatched | cancelled`，confirm 失败可重试。

### 6.2 草案生成

用户手动派发（主对话「派发任务」入口 → 输入需求描述）：

- 后端以 `Yuki.N.Invocation` 发起一次**有界内部模型调用**，结合该 Yuki 的
  人格上下文与用户描述，起草 `title` 与 `prompt`（任务指令全文）。
- 模型调用失败/超时：确定性回退——title 取描述首行截断，prompt 取描述
  原文。草案永远可生成。
- 草案同时携带**能力快照**（见 §6.3）与生成说明（`generationNote`）。

### 6.3 能力快照继承

派发时新任务的 ThreadConfig 按以下顺序解析（既有 `Semigroup ThreadConfig`
语义，左优先）：

```text
草案中的显式覆盖（用户在派发对话框修改）
→ Home 会话的 ThreadConfig（Yuki 级默认）
→ 全局默认（globalThreadConfig）
```

`incarnationId` 恒为当前 Yuki，不可在草案中改写。confirm 后写入任务自己
的 `threads-config/<thread>.json`，此后与 Home 配置各自独立演化。

### 6.4 Yuki 主动提议派发

主 Agent 获得新后端工具 `propose_dispatch`（仅 Home Run 与任务 Run 可见，
Worker 不可见）：

1. Yuki 判断聊天中的需求适合成为持久任务时调用，参数
   `{title, prompt, reason}`。
2. 后端创建 `source=agent` 的 DispatchDraft，向前端推 CUSTOM 事件
   `dispatch.draft`，前端在主对话流内渲染**派发卡片**（可编辑）。
3. 工具调用**阻塞等待用户裁决**（超时默认 10 分钟）：确认 → 工具返回
   `{threadId}`；取消/超时 → 工具返回拒绝，Yuki 继续对话。
4. 等待期间 run 处于 AwaitingTool；用户仍可 steer 或取消整个 run。

### 6.5 派发后

- confirm 创建任务 Thread（应用配置快照）并将 `prompt` 作为首条 user
  message 写入 Transcript；前端跳转任务视图并自动发起首个 Run。
- 幂等：仅当 Transcript 末条是未应答的 user message 时才自动发起。
- 任务立刻出现在集群总览与工作台的活跃状态中。

## 七、Subagent 与 Orchestration

### 7.1 三层委派关系

- 主 Agent Run 与任务 Agent Run 的 `runtimeDepth` 均为 1：可直接使用
  `sub_agent` 族工具。
- Worker Run 的 `runtimeDepth` 为 0：默认不可再委派。
- Worker 记忆边界沿用现状：继承只读记忆工具，`memory_remember` /
  `memory_void` / `self_update` / `sleep` 禁用。

### 7.2 同步 `sub_agent`（保留）

既有阻塞式工具保留不变。子 Run 事件仍以 `agent.sub` 包装进父流。

### 7.3 异步 Worker 工具组（新增）

| 工具 | 语义 |
| --- | --- |
| `sub_agent_spawn` | 异步派出 Worker：立即返回 `{agentId}`，Worker 后台 Run |
| `sub_agent_send` | 向运行中的 Worker 注入 steering 文本 |
| `sub_agent_status` | 查询单个 Worker 状态与结果摘要 |
| `sub_agent_list` | 列出本 Run 派出的全部 Worker 及状态 |
| `sub_agent_wait` | 阻塞等待一个/多个 Worker 完成（带超时），返回结果 |
| `sub_agent_cancel` | 取消 Worker |

语义规定：

- **事件流分离**：异步 Worker 的事件**不**包装进父 SSE 流。父 Run 通过
  `wait` 返回值与**完成通知注入**感知 Worker；前端通过遥测流展示 Worker
  状态（§八）。这避免多生产者并发写同一条 SSE 连接，也让父上下文不被
  Worker 过程噪声污染。
- **完成通知注入**：Worker 终止时，runtime 向父 Run 的 steering 队列注入
  系统消息（`[worker <id> finished: <结果摘要>]`），父 Run 在下一轮次
  边界自然看到。
- **生命周期级联**：父 Run 终止（任何结局）时，其派生的未完成 Worker
  全部被级联取消（递归）。需要「比父 Run 活得久」的工作应派发为任务。
- **结果回收**：Worker 终止时把最终文本与结局写入 RunRegistry 完成表；
  `wait`/`status` 由此读取；条目保留至父 Run 结束。
- **因果记录**：`Experience` 预留的 `delegationId` 自本轮起填充为 spawn
  的 tool call id。
- **并发上限**：单 Run 活跃异步 Worker 受 `YUKI_SUBAGENT_MAX_PARALLEL`
  （默认 4）限制；超出时 `spawn` 返回明确错误。

### 7.4 与用户通道的关系

用户对 Worker 的 steering 与取消**不经过**父 Agent：既有
`POST /agent/steer` / `POST /agent/cancel` 按 runId 寻址，前端 Run 监控
直接调用。与 Agent 间通信（`sub_agent_send`）是两条独立通道。

## 八、运行遥测与交付追踪（新后端子系统）

可观测性目标不能靠前端轮询 RunRegistry 的粗粒度信息达成。新增
**Telemetry 子系统**（Infrastructure 层），统一消费 run 生命周期事件并
投影为可查询、可推送的状态。三部分：

### 8.1 LiveStatus：每活跃 Run 的实时投影

- 经 `AgentHooks.observeEvent`（现有统一观察点）消费事件流，维护
  `IORef (Map runId LiveStatus)`；注册/注销与 Run 生命周期同步。
- LiveStatus 内容：phase（running / awaiting-tool / compacting / sleeping /
  cancelling）、当前轮次与上限、模型链、累计 token（来自 `usage` 事件）、
  上下文估算与触发线（来自 `context.status` 事件）、进行中的工具调用
  （callId、名称、开始时间）、最近活动时间与摘要、活跃 Worker 数、
  objective（首条用户输入截断）、启动时间。
- 同步与异步 Worker 都有 LiveStatus；Worker 树经 parentRunId 组出。

### 8.2 交付台账（Deliveries）

记录每个 Yuki「交付了什么」：

- **最终回答**：根 Run（Home / 任务）正常结束时，答案摘要入台账。
- **Artifact**：工具输出溢出产生 artifact 时入台账。
- **文件写入**：经写工具成功的文件创建/修改入台账（与 §8.3 共用拦截）。
- 追加写入 `<dataDir>/deliveries.jsonl`；按 incarnation / thread / run
  可检索。Worker 的最终文本不入交付流（它经父 Run 汇报；其文件写入与
  artifact 正常入台账并归属所属任务）。

### 8.3 FS 变更台账（FsChanges）

按「工具拦截 + git 增强」策略追踪：

- **工具拦截（权威）**：在工具装配层包装 fs 写/编辑工具，成功后记录
  路径、操作（created / modified / deleted）、unified diff（有界，≤ 8KB；
  复用 `Domain.Diff`）。artifact 创建同样记录。
- **git 增强**：根 Run 终局时，若任务 cwd 位于 git 仓库，执行只读的
  `git status --porcelain` / `git diff --stat`（超时 3s，失败静默），与已
  记录路径求差，补记 `origin=git` 的变更（只留 stat，不留全文）——覆盖
  shell 命令等绕开工具的修改。
- 非 git 目录中 shell 造成的修改标记「未经追踪」，不谎报完整。
- 追加写入 `<dataDir>/fs-changes.jsonl`。

### 8.4 监控 SSE 流

- `GET /activity/stream`：单条 SSE 流多路复用**全部** Run 的遥测——
  连接建立先发 FleetSnapshot（全量），随后推送增量（status / delivery /
  fschange / notice）。同 run 状态推送节流合并（200ms）。
- ActivityHub（TChan 广播）汇集各 projector 的输出；每个 SSE 连接
  dupTChan 消费。这是前端集群总览与工作台的主数据源。
- `GET /incarnations/:id/activity`（富化版快照）保留，供初始加载与降级
  轮询。
- Run 级详细事件流仍是既有 `POST /agent` SSE 与 journal trace 端点；
  监控流只承载状态投影，不复制事件正文。

### 8.5 与既有机制的关系

- 不改 run loop：projector 全部经 hooks 与工具包装接入，runAgent 本体
  只增加终局通知（交付记录、git 增强、完成表写入三处小钩子）。
- 遥测是**投影**，不是新的事实源：事实仍在 Journal / Transcript /
  Task Archive / Artifact；遥测存储可删可重建（LiveStatus 易失；
  deliveries / fs-changes 是台账日志，重放 journal 可重建，但本轮不提供
  重建工具）。

## 九、记忆边界（本轮涉及的仅有规定）

1. 主对话与全部任务共享同一 incarnationId：记忆体系零改动。
2. 派发任务的 Transcript 以确认后的 prompt 开篇，任务经历归属该任务
   Thread；长期记忆归属 Yuki，与现状一致。
3. Worker 记忆权限不变（只读 + 禁写身份）；异步化不改变此边界。
4. 主对话的 FocusFrame / 睡眠沿用既有 per-thread 机制，不做特殊化。
5. `delegationId` 开始填充（§7.3），这是本轮对记忆系统的唯一写入路径
   改动。

## 十、不变式

1. 每个 Incarnation 至多一个 Home 会话；Home 不可归档、删除、fork，不
   出现在任务列表。
2. 派发任务只能经 DispatchDraft confirm 产生；Yuki 提议派发必须经用户
   确认，无静默派发。
3. 派发任务的 `incarnationId` 恒等于其 Yuki；能力快照在 confirm 时固化，
   此后任务配置独立演化。
4. Worker 是 Run 内临时执行者：父 Run 终止则其未完成 Worker 级联取消；
   Worker 不形成持久主体。
5. 异步 Worker 事件不写入父 SSE 流；父 Run 感知 Worker 只经 `wait` 与
   steering 注入。
6. Worker 不得持有宽于父级的工具集；`workerDeniedTools` 边界在同步与
   异步路径上一致。
7. 每个活跃 Run 都可按 runId 取消与 steer，无论根 Run 还是 Worker。
8. 遥测是投影：LiveStatus 易失，deliveries / fs-changes 为追加台账；
   历史真相仍由 Journal、Transcript 与 Task Archive 承担。
9. 主对话与任务的记忆行为一致；本轮不改变任何记忆写入语义（除填充
   `delegationId`）。
10. 所有新端点与事件对旧客户端可忽略、可降级。
11. FS 变更追踪不谎报：工具拦截为权威记录；git 增强只覆盖仓库内变化；
    其余明确标记未经追踪。
12. 监控流只承载状态投影；Run 级事件正文仍由 `POST /agent` 与 journal
    trace 承担。

## 十一、分期

详见 [`03-任务列表.md`](03-任务列表.md)。概要：

- **P0｜地基**：SessionKind；Run 树索引；Telemetry 子系统（LiveStatus
  投影、交付与 FS 台账、ActivityHub）。
- **P1｜集群与工作台闭环**：Home 会话；手动派发；监控 SSE 流与富化
  activity；前端新骨架——集群总览、Yuki 工作台（现在 / 主对话 / 任务 /
  交付 / 变更）、Run 监控。
- **P2｜主动编排**：`propose_dispatch` 与派发卡片；异步 `sub_agent_*`
  工具组；完成通知注入与级联取消；Worker 直达 steering。
- **P3｜对齐蓝图 M4**：Delegation Spec 结构化、Work Graph 雏形、预算
  治理、activity 历史维度。

## 十二、验收场景

- 打开产品默认进入集群总览；多位 Yuki 的状态卡片实时更新（经监控流，
  非整页轮询）。
- 选择任意 Yuki 进入工作台；主对话可聊天，不创建任务。
- 主对话中派发任务：草案可编辑；确认后任务开始执行；集群总览、工作台
  「现在」、任务视图同步可见。
- 运行中的 Run 展示阶段、轮次、token、上下文用量、进行中工具与耗时；
  数据与 run 实际行为一致（对照 journal）。
- Yuki 在聊天中提议派发，用户确认/修改/拒绝三种路径行为正确。
- 任务 Agent 派出多个 Worker：工作台显示三层树；用户可直达 steer/取消
  任一 Worker；父 Run 收到完成通知并整合结果。
- 取消父 Run，其全部未完成 Worker 随之终止。
- 任务通过写工具创建/修改的文件出现在「变更」视图且 diff 正确；git
  仓库中 shell 造成的变更在 run 结束后补记（origin=git）；非仓库目录
  shell 变更不谎报。
- 根 Run 的最终回答、产生的 artifact、文件写入出现在「交付」视图。
- 重启服务后：Home 会话、任务、派发草案、交付与变更台账仍在；活跃
  状态不谎报（归零）。
- Worker 无法调用 `memory_remember` 等禁具；主对话经历正常进入记忆
  体系。
