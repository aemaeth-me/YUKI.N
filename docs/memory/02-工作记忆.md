# 工作记忆（Working Memory）与睡眠-清醒循环

> 源码：`../../src/Yuki/N/Memory/Working.hs`，编排与睡眠：`../../src/Yuki/N/Cognition.hs`，上下文纪元：`../../src/Yuki/N/ContextEpoch.hs`

## 1. 概念定位

工作记忆是**当前进行中的短期状态**：化身正在做什么、每个任务的开环、暂定主张、
最近结果、以及经验流消费到的位置（cursor）。它不是聊天历史——聊天历史在任务档案里；
它是「头脑里的桌面」。

设计隐喻是**睡眠**：上下文拥挤时，化身（或系统）请求睡眠；一个专门的 sleep 模型
「做梦」——决定什么该忘、什么该留、写一段续接语；产出 **Wake Packet**；醒来后带着
干净上下文继续**同一个任务**。睡眠是「先遗忘的工作记忆维护」，不是长期记忆的写入
（长期记忆靠任务档案自动追加）。

## 2. 状态机

### 2.1 工作记忆头 `WorkingMemoryHead`（每化身一个）

| 字段 | 含义 |
|------|------|
| `id` / `incarnationId` | `working/<化身>` |
| `revision` | 单调修订号，所有迁移的乐观锁 |
| `status` | 见下 |
| `cursor` | 经验流光标（streamId + seq） |
| `checkpointId` / `wakePacketId` | 最近一次睡眠产出的检查点/唤醒包引用 |
| `activeTaskId` | 当前活动任务（焦点） |
| `focusFrames` | 该化身全部任务的焦点帧（Map task → FocusFrame） |
| `degradedReason` | 降级原因（恢复失败时） |
| `created` / `updated` | 时间戳 |

### 2.2 工作状态 `WorkingStatus` 与睡眠循环状态 `SleepCycleStatus`

```
WorkingStatus:  awake → quiescing → asleep → waking → awake
                        ↘ degraded（任意中断点可进入，仅可恢复）

SleepCycleStatus: quiescing → prepared → asleep → waking → awake
                        ↘ degraded
```

| 迁移 | 操作（WorkingStore 方法） | 校验 |
|------|------|------|
| awake→quiescing | `workingRequestSleep` | revision 匹配；头状态 = awake；任务必须有焦点帧；cycleId/task/baseEpoch 非空；cycle 不重复 |
| quiescing→prepared | `workingPrepareCheckpoint` | 头 = quiescing；cycle = quiescing；检查点与唤醒包**交叉校验**（见下） |
| prepared→asleep | `workingCommitSleep` | 头 = quiescing；cycle = prepared；检查点/唤醒包必须已存在 |
| asleep→waking | `workingBeginWake` | 头 = asleep；cycle = asleep |
| waking→awake | `workingCommitWake(Focus)` | 头 = waking；cycle = waking；回放光标只进不退；新焦点帧校验 |
| 任意→degraded | `workingAbortSleep` / `workingDegradeWake` | 原因非空；分别从 quiescing / waking 进入 |

`workingRecover`：非 awake 状态可直接恢复为 awake（含从 degraded），并生成降级原因。

### 2.3 `validatePrepared` —— 检查点与唤醒包的交叉校验

提交检查点前必须全部通过（否则拒绝，睡眠中止）：

- 检查点与唤醒包：化身、任务、run、baseEpoch、trigger 与睡眠循环一致；
- 检查点 `baseRevision == expected`；`coveredThrough == 冻结光标 == 当前工作光标`
  （quiescence 后光标不许再动）；
- 检查点 `wakePacketId` 指向该唤醒包；
- 检查点焦点闭包 `==` 当前头焦点帧、活动任务一致；
- 检查点/唤醒包 ID 不重复；checkpoint stateRef、sourceClosureHash、payloadRef 非空。

### 2.4 焦点帧 `FocusFrame`（每化身×任务一个）

| 字段 | 含义 |
|------|------|
| `id` / `incarnationId` / `taskId` | 域标识 |
| `revision` | 从 1 起，严格 +1（新帧必须 1，旧帧必须 current+1） |
| `status` | `active` / `parked` / `closed` |
| `epochId` | 当前上下文纪元 |
| `objective` | 任务目标（睡眠后续接语会覆盖它） |
| `activeItems` / `openLoops` / `provisionalClaims` | 进行中的事项（≤8 的派生自唤醒包） |
| `recentOutcomeRefs` | 最近 ≤12 个结果事件 ID |
| `artifactRefs` | 产物引用 |
| `cursor` | 帧内经验光标：不得超前于工作头光标、不得为负 |

焦点帧是睡眠「保留什么」的锚点：睡眠针对 `activeTaskId` 对应的帧，醒来后帧被唤醒包内容更新。

## 3. 睡眠（Sleep）全流程

入口有三处（`Cognition.hs`）：

1. **模型自请**：`sleep` 工具（`SleepCall reason`）→ 写入 `cognitionSleepRequests` 集合
   （key = 化身×runId）→ 下一个 `shouldSleep` 钩子消费返回 True。
2. **软上限**：上下文压缩后（`afterCompaction`）自动睡。
3. **硬性**：provider 溢出（emergency compaction）后自动睡。

### 3.1 梦境（Dream）—— `sleepCompaction` 的模型调用

前置：`workingReady` 保证工作记忆存在且 awake、光标追到经验流头、焦点帧就位；
`contextEpochProject` 把当前上下文投影为段（segment）目录。

调用规格：kind=`working.sleep`，promptRevision=`sleep-dream/v1`，2 次尝试，
输出 16000 字符，超时 60s。

**系统提示词**（节选）：

```
You are the dedicated sleep model for a Yuki incarnation.
Sleep is forget-first working-memory maintenance, not long-term memory creation.
Return strict JSON only with keys:
continuation: concise text sufficient to resume the same task;
activeItems: up to 8 current facts/actions held provisionally;
openLoops: up to 8 unresolved items;
forgotten: array of {subject, reason, sourceSegmentIds};
retainedSegmentIds: only ids from the supplied segment catalog, up to 12.
Decide deliberately what can disappear from the active context. Do not preserve everything.
Do not invent facts or promote durable memory.
```

用户侧输入：化身 JSON、任务、触发器、当前焦点帧、段目录（有界，按预算自适应：
catalog ≤160 条、detail ≤48 条、payload ≤1/8 预算）——**目录只给 id/kind/authority/sourceRef，
详情只给被选中的最近段**，防止睡眠模型被整段历史淹没。

**校验 `parseDream`**：continuation 非空（≤6000）；activeItems/openLoops ≤8；retained ≤12
且必须 ∈ 目录；forgotten ≤32 且 subject/reason 非空、sourceSegmentIds ∈ 目录。

### 3.2 落盘（`commitSleep`）—— 状态机推进

1. `retainedWakeMessages`：从投影段里选出 retained 段，转回 AGUI 消息；
   工具调用/结果按因果组配对（只有 call 与 result 同时被保留才都保留）。
2. 唤醒包 JSON payload、quiescing 头 JSON payload 分别写 Blob（`persistPayload`，
   标签 `wake-packet` / `working-checkpoint`，blobAttach 附加出处）。
3. `WakePacket`：id、化身、任务、run、baseEpoch、trigger、continuation、activeItems、
   openLoops、forgotten、retainedSegmentIds、payloadRef、generatorRevision、
   invocationRef、created。
4. `WorkingMemoryCheckpoint`：id、baseRevision、coveredThrough（冻结光标）、
   焦点帧闭包、activeTaskId、stateRef（quiescing 头 JSON）、
   `sourceClosureHash = SHA-256(epochHash + cursor + frames)`、wakePacketId、created。
5. `workingPrepareCheckpoint` → `workingCommitSleep`（头进入 asleep）。
6. `commitWakeEpoch`：把保留段 + 唤醒包段（`SegmentWakePacket` / `AuthorityDerived`）
   提交为新**上下文纪元**（parent = baseEpoch）。
7. `workingBeginWake` → 取经验头光标作回放位置 → `workingCommitWakeFocus`：
   焦点帧被更新为 `wakeFocusFrame`（revision+1、epochId=新纪元、objective=continuation、
   activeItems/openLoops 来自唤醒包、provisionalClaims 清空、cursor=回放位置）。
8. `wakeCompaction`：把压缩结果替换为「保留的指令段 + 唤醒包渲染文本 + 保留消息」，
   丢弃原摘要/唤醒包标记段。

任何一步失败 → `degradeWaking`/`degradeAsleep`：头进入 degraded、循环进入 degraded、
失败原因写入审计，但**不丢数据**（检查点/唤醒包已在 Blob 与存储中）。

### 3.3 Wake Packet 的渲染（进入新上下文的样子）

```text
[wake packet — derived working memory]
id: <id>
continuation: <续接语>
[active]
- <activeItems…>
[open loops]
- <openLoops…>
This packet is a derived short-term checkpoint. It is not long-term memory and contains no
automatically recalled facts.
Forgotten material remains only in the sleep audit (<n> decisions).
```

睡眠循环本身也记入任务档案（`archiveEntries` 把 `[wake packet …]` 开头的内容归档为
`wake-packet` 类条目）与上下文纪元（`SegmentWakePacket`），全链路可审计。

### 3.4 触发器 `SleepTrigger`

`soft_limit`（软上限压缩后）、`provider_overflow`（紧急压缩后）、`manual`（HTTP 手动）、
`self_requested`（模型 sleep 工具）、`suspend`（挂起）。

## 4. 恢复（Recovery）—— 断电/崩溃自愈

启动时 `cognitionRecover` 对每个非 awake 的工作记忆头执行：

| 状态 | 恢复动作 |
|------|------|
| quiescing + cycle=quiescing | `workingAbortSleep`：「睡眠在检查点提交前被中断，未应用任何遗忘」 |
| quiescing + cycle=prepared | 继续 `commitSleep` → asleep → 正常唤醒 |
| asleep | `ensureRecoveryWake`（唤醒包/唤醒纪元缺失则从 baseEpoch 重建）→ beginWake → commitWake |
| waking | 同上 → commitWake（光标滞后则用经验头补回放） |
| degraded | 直接 `workingRecover`，保留原降级原因 |

`workingRecover` 内部还做**过渡元数据一致性诊断**（`recoveryFailure`）：例如
「睡眠被中断于检查点提交前」「唤醒无法完成恢复，从持久上下文头继续」等，写入
`degradedReason` 与循环的 `failure` 字段——恢复不是静默的，每次降级都有文字原因。

磁盘加载时 `validateState` 做整体一致性校验：key 匹配、cursor 流匹配、焦点帧有效、
checkpoint/wakePacket 引用存在、活动任务必须有帧等。

## 5. 并发与一致性

- 全部存储操作在单一 `MVar` 内串行化；每次迁移都要求调用方提供**期望 revision**，
  不匹配即 `Left "stale working memory revision: …"`。
- 睡眠全流程跨多个存储操作，由 `withIncarnationLock`（按化身的 MVar 锁）保证同一化身
  的睡眠/固化/归档不交错。
- 经验流光标 `advance` 只进不退、流 ID 必须匹配，是工作记忆与经验流之间的对齐约束。
