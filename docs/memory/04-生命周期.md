# 生命周期：数据流、钩子集成、并发与恢复

> 编排核心：`../../src/Yuki/N/Cognition.hs`；钩子定义：`../../src/Yuki/N/Agent.hs`；调用框架：`../../src/Yuki/N/Invocation.hs`

## 1. 认知层（Cognition）—— 所有记忆的编排者

`Cognition` 聚合八个存储 + 基础设施，是记忆系统的「神经系统」：

```haskell
data Cognition = Cognition
  { cognitionBlobs        :: BlobStore,          -- 内容寻址存储（档案内容、检查点、唤醒包、经验负载）
    cognitionExperiences  :: ExperienceStore,    -- 经验流
    cognitionIncarnations :: IncarnationStore,   -- 化身与提示词谱系
    cognitionContexts     :: ContextEpochStore,  -- 上下文纪元（睡眠保留段的投影依据）
    cognitionArchive      :: TaskArchiveStore,   -- 任务档案（长期记忆本体）
    cognitionWorking      :: WorkingStore,       -- 工作记忆（睡眠-清醒）
    cognitionLongTerm     :: LongTermStore,      -- 记忆库（HTTP 索引）
    cognitionImpressions  :: ImpressionStore,    -- 印象（潜意识层）
    cognitionModels       :: [Model],            -- 模型链
    cognitionJournal      :: Maybe Journal,      -- 审计日志
    cognitionSleepRequests :: MVar (Set (Text, Text)),          -- sleep 工具请求队列
    cognitionActivationCache :: MVar (Map (Text, Text, Text) Text), -- 激活缓存
    cognitionContextCache   :: MVar (Map (Text, Text, Text) Text), -- 纪元缓存
    cognitionRunLocks       :: MVar (Map Text (MVar ()))          -- 按化身串行锁
  }
```

## 2. Agent 钩子 —— 记忆在 run 生命周期中的五个介入点

`cognitionHooks`（叠加在 `defaultHooks` 上）与旧版 `memoryHooks` 可以并存：

| 钩子 | 时机 | 记忆动作 |
|------|------|------|
| `transformContext` | 每轮模型请求前 | ① `ensureAguiContext`：把输入消息提交为上下文纪元、保证工作记忆/焦点帧就位；② `activationText`：激活印象，注入 cues |
| `observeEvent` | run 开始 & 每次工具结果 | `RunStarted`→归档用户输入为档案 run（running）；`ToolCallResult`→归档工具结果 |
| `shouldSleep` | 每轮决策点 | 消费 `sleep` 工具请求（化身×runId 集合） |
| `afterCompaction` | 上下文压缩后 | 归档压缩前消息 → 提交纪元 → `sleepCompaction` 全流程（软上限/溢出/自请） |
| `afterRunOutcome` | run 结束后 | `closeExperience`：归档最终 run（completed/failed/cancelled）→ 追加经验事件 → 入固化队列 → 推进工作记忆光标与焦点帧 |

钩子**只对根 run 生效**（`isRoot`：无 parentId）；子代理（sub_agent）不触发记忆写入。

## 3. 写入路径（run → 长期记忆 → 印象）

```
用户输入/工具结果/助手输出
   │  observeEvent（运行中，running 状态）＋ afterRunOutcome（终态）
   ▼
Task Archive 追加（archiveTaskSnapshot）
   内容哈希防变、条目去重、run 合并语义
   │
   ▼
经验流追加（appendRunEvents）
   UserInputAccepted / AssistantOutcomeRecorded / RunTerminated
   │
   ├─► 工作记忆：光标推进、焦点帧 recentOutcomeRefs ≤12
   │
   └─► 固化队列（enqueueConsolidation → forkIO drain）
         │  ImpressConsolidationRequested 事件（幂等）
         ▼
      experienceClosure（事件+payload，≤50000 字符）
         ▼
      consolidateImpression（独立模型，v3 prompt，CAS 提交）
         ▼
      ImpressConsolidationSucceeded/Failed 事件（幂等，重启可续）
```

## 4. 读取路径（意图 → 线索 → 验证）

```
新一轮 run
   │  transformContext
   ▼
currentIntent（最新用户文本；intentId 稳定化）
   │  缓存命中？直接复用
   ▼
activateImpression（独立模型，v2 prompt）
   输入：印象状态 + 意图 + 档案目录(≤64 Task ID)
   输出：≤5 cues（校验：hint 非空、confidence∈[0,1]、memoryIds∈目录）
   ▼
渲染 [impression cues — non-factual] 注入消息流头部
   │
   ▼
主模型：自行决定是否 memory_grep（固定串扫描档案）
   │  命中 → memory_read（有界窗口精读，截断显式）
   ▼
引用证据（taskId/entryId/runId 进回复）
```

**印象→档案→验证**是强制链路：线索只能建议 grep；grep 结果带证据类别与完整度；
read 显式截断。三层校验让「模型声称记得」在架构上无法成立——记得必须可指向条目。

## 5. 工具面（代理可见的记忆能力）

| 工具 | 作用 |
|------|------|
| `memory_grep` | 固定串扫描任务档案；源证据优先、进程记录默认排除、分页与截断透明；默认排除当前任务 |
| `memory_read` | 锚定条目读有界窗口；对话树闭合；字符预算偏向锚点 |
| `self_inspect` | 查看化身身份、active prompt、工作记忆头、印象状态 |
| `self_update` | 更新化身 direction/name/impressionModel → 自动生成可审计的 charter 修订，显式激活 |
| `sleep` | 请求下一认知边界睡眠（可带原因） |

`memory_remember` 之类的「手动写入记忆」工具**不存在**——这正是宪法
「没有手动把一句话变成记忆的动作」的体现。

## 6. 并发、幂等与失败隔离

### 6.1 三层并发控制

1. **存储内乐观锁**：所有写操作要求调用方带期望 revision（working、impression、
   incarnation、long-term、experience 光标），不匹配即失败——并发写绝不静默覆盖。
2. **按化身串行锁**：`withIncarnationLock`（MVar 池）把同一化身的归档、睡眠、固化
   串行化，跨存储的复合流程（睡眠五步）不会交错。
3. **幂等事件**：`appendExperienceIdempotent` 按 operationId+kind 查重；
   固化队列由经验流驱动，重启后 `resumeConsolidations` 自动续跑。

### 6.2 失败隔离

- 记忆钩子外层 `insulate`/`shield`：捕获一切异常（除 async 中断），记忆失败
  只记日志/审计，**主对话照常**。
- 激活失败 → 无 cues 注入；固化失败 → Failed 事件 + 错误入 payload；
  睡眠失败 → degraded 状态 + 文字原因。
- 模型调用统一走 `Invocation`：限时、限输出、逐模型重试、journal 全记录。

## 7. 审计与回放

- **Journal**（`journal.jsonl`）：每次模型调用（含激活/固化/梦境子调用，scope 嵌套
  `run → memory|working.sleep|impression.activate|impression.consolidate → invocation → attempt`）
  的 request/event/finish 全记录；`store.brief`/`store.facts` 记录记忆注入内容。
- **Replay**（`../../src/Yuki/N/Replay.hs`）：按 journal 逐字节重放模型输入与工具结果，
  与真实事件流比对求第一个分歧（`Divergence`）。含记忆注入的 journal 用
  `replayWithStores`：以记录的 ThreadBrief/Fact 快照重放 watcher，保证确定性；
  CLI 的 `replayFile` 检测到记忆注入则拒绝（防静默偏差）。
- **经验流 + 审计记录**（activation/revision/sleep cycle/receipt）：记忆系统自身的
  全部状态变化都可追溯——「印象从哪条经验来、为什么改、由哪个模型调用产生」。

## 8. 化身与提示词谱系

- `Incarnation`（id/name/direction/impressionModel/revision/status）是记忆的主体边界：
  档案、工作记忆、印象、经验全部按化身分域。
- 提示词分层：Root Constitution（根，可编辑/激活/回退）→ Incarnation Charter
  （由根+direction 生成，含工作风格/判断倾向/工具策略/记忆策略/自我管理/边界六节）→
  task-local 指令。记忆策略来自 Root Constitution 的记忆章节（见 README 总览）。
- `self_update` 生成的 charter 是**修订**而非改写：draft → 检查 → activate，
  旧版 retired，全程可审计。

## 10. 一图流：一次完整交互中记忆系统的全部动作

```
用户发消息
  ├─ transformContext: 提交纪元 / 工作记忆就位 / 激活印象注入线索（缓存化）
  ├─ 主模型: memory_grep → memory_read 验证 → 回复
  ├─ observeEvent: 工具结果实时归档（running）
  ├─ (上下文超限) afterCompaction: 归档 → sleep: 做梦→忘→Wake Packet→新纪元→醒
  └─ afterRunOutcome: 档案终态提交 → 经验事件×3 → 光标/焦点帧推进 → 固化队列
       └─ 后台: 经验闭包 → 固化模型 → 印象集 v+1（CAS）→ Succeeded/Failed 事件
```
