# 03 派发任务

派发把一项工作交给这位 Yuki 的**任务 Agent** 长期执行。任务与主对话
分离：有独立对话、独立运行历史，可暂停、可继续。

## 两个入口

**你发起**：主对话头部「派发任务」→ 输入需求描述。

**Yuki 提议**：聊天中 Yuki 判断需求该成为持久任务时，对话流内会出现一
张派发卡片（它调用了 `propose_dispatch` 工具并阻塞等你裁决）。

两个入口殊途同归，都进入同一份**派发草案**。

## 草案

草案包含：

- **标题**（可编辑）
- **任务 Prompt**（可编辑）：任务 Agent 收到的第一条指令
- **能力快照**（只读摘要）：provider / model / effort、cwd、fs / shell /
  memory gate、上下文策略。默认继承这位 Yuki 的主对话配置；当前版本
  不可在界面修改（见 [10-已知限制](10-已知限制.md)）。
- **生成说明**：由模型起草，或模型不可用时按原文生成。

草案持久保存：刷新、重启都不丢。同一位 Yuki 可以有多份待确认草案，
它们列在「现在」视图的顶部等待区。

## 确认之后

1. 创建任务（携带能力快照与这位 Yuki 的身份）。
2. 任务 Prompt 成为任务对话的第一条指令。
3. 页面跳到任务对话，首个 Run 自动开始（仅当这条指令尚未被应答——
  刷新页面不会重复启动）。
4. 集群总览与「现在」视图立刻出现该任务的运行状态。

取消草案则什么都不发生；Yuki 提议被取消时，它会收到拒绝并继续聊天。

## 任务执行期间

- 任务 Agent 是 Orchestrator：它可以自己干，也可以派 Worker（见
  [04-Subagent与编排](04-Subagent与编排.md)）。
- 你在任务对话里继续追问、steer、取消，用法与主对话相同。
- 任务的交付与文件变更会归属到该任务，出现在「交付」与「变更」视图。

## 语义边界

- 任务继承这位 Yuki 的人格与记忆（同一份长期记忆体系），但拥有独立的
  对话历史与任务级配置。确认后，任务配置与主对话配置各自独立演化。
- 任务 Agent 也可以再提议派发（嵌套派发），确认流程相同。
